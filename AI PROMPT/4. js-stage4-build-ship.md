# JavaScript Fullstack — Giai đoạn 4: Build & Ship

**Mục tiêu:** Biến kiến thức thành kinh nghiệm thật. Đây là nơi mọi thứ từ Giai đoạn 1-3 được kiểm chứng.  
**Yêu cầu trước:** Đang trong hoặc đã xong Giai đoạn 2. Không cần xong hoàn toàn Giai đoạn 3 mới bắt đầu.  
**Nguyên tắc:** Shipped is better than perfect. Done is better than optimal.

---

## Tại sao Giai đoạn 4 khác hoàn toàn

Giai đoạn 1-3 có câu trả lời đúng. Giai đoạn 4 thì không.

Không có tutorial nào dạy bạn cảm giác khi production down lúc 2 giờ sáng và bạn không biết tại sao. Không có sách nào dạy bạn quyết định có nên break backwards compatibility để ship feature quan trọng. Không có course nào simulate được áp lực khi user report bug mà bạn không reproduce được.

Giai đoạn 4 không phải học thêm — là **trả học phí bằng kinh nghiệm thật**.

---

## PHẦN 1 — Chọn Idea Đúng

### Tiêu chí của một project tốt để học

Không phải mọi project đều dạy bạn như nhau. Một project tốt cần có đủ 4 tiêu chí:

**1. Có user thật ngoài bạn**
Dù chỉ 5-10 người. User thật tạo ra áp lực thật — không thể "fix sau" khi ai đó đang dùng và bị broken.

**2. Giải quyết vấn đề thật**
Không phải clone app nổi tiếng. Không phải "tôi muốn học X nên build Y". Phải là thứ người khác thật sự muốn dùng — dù nhỏ.

**3. Đủ phức tạp về kỹ thuật**
Cần có ít nhất: auth, database, API, một tính năng real-time hoặc async processing. Quá đơn giản thì không học được gì mới.

**4. Đủ nhỏ để ship trong 4-8 tuần**
Quá lớn thì không bao giờ ship. Không ship = không học được gì từ Giai đoạn 4.

---

### Framework chọn idea

Trả lời 3 câu hỏi:

```
1. Vấn đề tôi gặp hàng ngày mà tool hiện tại giải quyết không tốt là gì?
   → Tìm trong công việc, side projects, cuộc sống

2. Ai khác cũng gặp vấn đề đó?
   → Nếu chỉ mình tôi gặp → too niche
   → Nếu quá nhiều người gặp → competition quá cao

3. Tôi có thể build MVP trong 4 tuần không?
   → Nếu không → cắt scope, không đổi idea
```

---

### Ví dụ ideas phù hợp

**Tốt:**
- Tool tổng hợp notifications từ nhiều nguồn (GitHub, Jira, Slack) thành một feed
- App theo dõi chi tiêu cho freelancer với invoice generation
- Tool monitor uptime cho side projects của developers
- Platform quản lý snippet code với search và tagging
- App quiz tạo từ tài liệu upload (như NotebookLM nhỏ)

**Không tốt:**
- "Tôi build Twitter nhưng tốt hơn" → quá lớn, không rõ differentiator
- "Todo app với AI" → không có user thật nào cần thêm todo app
- "Marketplace cho X" → two-sided marketplace cực khó, cold start problem
- "Social network cho Y" → network effects không thể fake

---

### Scoping đúng — quan trọng nhất

Hầu hết project thất bại vì scope quá lớn, không phải vì idea tệ.

```
Rule: Lấy scope bạn nghĩ là MVP, cắt còn 50%.

Bạn nghĩ MVP cần:
  - Auth (email + Google)
  - Dashboard
  - Core feature A
  - Core feature B
  - Settings page
  - Email notifications
  - Mobile responsive

Thật ra MVP chỉ cần:
  - Auth (email only)
  - Core feature A (feature B là v2)
  - Đủ để 10 người dùng và cho feedback
```

## PHẦN 2 — Từ Zero Đến V1

### Thứ tự build đúng

Nhiều người bắt đầu từ UI rồi mới nghĩ tới backend, database, auth. Sai thứ tự làm mất nhiều thời gian refactor.

```
Thứ tự đúng:

Week 1: Foundation
  → Setup project (monorepo hoặc single repo)
  → Database schema v1
  → Auth (đừng tự build, dùng library)
  → Deployment pipeline (CI/CD từ ngày 1)

Week 2-3: Core Feature
  → API endpoints cho core feature
  → UI cho core feature
  → Happy path chạy end-to-end

Week 4: Production-Ready
  → Error handling
  → Logging cơ bản
  → Monitoring cơ bản
  → Security checklist
  → Beta users (5-10 người)

Week 5-6: Feedback Loop
  → Fix bugs từ beta users
  → Polish UX
  → Public launch
```

---

### Checklist trước khi ship cho user thật

Đây là thứ **tối thiểu** cần có. Không phải perfect — là đủ để không bị cháy nhà.

#### Auth & Authorization
- [ ] Password hashed (Argon2 hoặc bcrypt) — không bao giờ plain text
- [ ] JWT/Session có expiry — không phải infinite
- [ ] Refresh token stored trong HttpOnly cookie
- [ ] Rate limiting cho login endpoint — chống brute force
- [ ] Email verification (nếu cần)
- [ ] Authorization checks — không chỉ authentication. Kiểm tra ownership

#### Input & Data
- [ ] Validate mọi input từ client — server-side, không tin client
- [ ] Parameterized queries / ORM — không concatenate SQL string
- [ ] File upload validation — type, size, không execute uploaded files
- [ ] CORS configured đúng — không dùng `*` trong production
- [ ] Rate limiting cho public APIs
- [ ] Request size limits — chống payload attacks

#### Error Handling
- [ ] Global error handler — không để unhandled errors crash server
- [ ] Error messages cho user không leak internal details
- [ ] Unhandled promise rejections được catch
- [ ] 404 và 500 pages không leak stack traces
- [ ] Graceful shutdown — xử lý SIGTERM, drain requests

#### Logging & Monitoring
- [ ] Structured logs (JSON) — không plain text
- [ ] Log errors với stack trace và context
- [ ] Error tracking (Sentry free tier) — biết khi có lỗi, không đợi user report
- [ ] Uptime monitoring (Better Uptime, UptimeRobot free tier)
- [ ] Basic metrics — response time, error rate

#### Database
- [ ] Database backups automated — test restore ít nhất 1 lần
- [ ] Connection pooling configured
- [ ] Database credentials không hardcoded, dùng env vars
- [ ] Migrations tested trên staging trước production
- [ ] Indexes cho queries thường dùng

#### Infrastructure
- [ ] Environment variables quản lý đúng — không commit `.env` production
- [ ] HTTPS — không HTTP
- [ ] Security headers — HSTS, X-Frame-Options, CSP cơ bản
- [ ] Dependencies updated — không có known vulnerabilities (`npm audit`)
- [ ] `node_modules` không bao giờ commit

#### Deployment
- [ ] CI/CD pipeline — không deploy bằng tay
- [ ] Staging environment — test trước khi push production
- [ ] Rollback strategy — biết làm gì khi deploy fail
- [ ] Zero-downtime deployment (hoặc ít nhất biết downtime window)

### Những thứ cố ý KHÔNG làm ở V1

V1 không cần và không nên có:

```
✗ Microservices           → monolith trước
✗ Kubernetes              → Vercel/Railway đủ dùng
✗ Full observability      → Sentry + uptime monitoring là đủ
✗ 100% test coverage      → test happy path và critical paths
✗ Perfect code            → working code trước, refactor sau
✗ Multi-region            → single region trước
✗ Custom auth             → dùng library
✗ Real-time nếu không cần → polling đơn giản hơn nhiều
✗ Mobile app              → web first
```

## PHẦN 3 — Những Thứ Chỉ Học Được Khi Có User Thật

### 3.1 — Incident Response

Sẽ có lúc production down. Không phải "nếu" — là "khi nào". Chuẩn bị trước.

**Runbook cơ bản cần có:**

```markdown
# Runbook: Production Down

## Symptoms
- Error rate > 1% trong 5 phút
- Uptime monitor alert
- User reports

## Diagnosis Steps
1. Check error tracking (Sentry) → lỗi gì, bao nhiêu users bị ảnh hưởng
2. Check logs → error message, stack trace
3. Check recent deploys → có deploy gần đây không
4. Check database → connections ok? queries slow?
5. Check external services → Stripe, email, storage down?

## Common Fixes
- Deploy fail → rollback: [link hướng dẫn rollback]
- Database connection exhausted → restart connection pool
- Memory leak → restart server
- Third-party service down → enable maintenance mode

## Communication
- Update status page nếu downtime > 5 phút
- Notify users nếu data affected
```

**Postmortem template (blameless):**

```markdown
# Postmortem: [Incident title] — [Date]

## Summary
[1-2 câu mô tả incident và impact]

## Timeline
- 14:32 — [Event]
- 14:45 — [Detection]
- 15:01 — [Mitigation]
- 15:20 — [Resolution]

## Root Cause
[Không phải "ai làm sai" — là "hệ thống nào failed và tại sao"]

## What Went Well
- [Thứ detect nhanh]
- [Thứ mitigation hiệu quả]

## What Could Be Better
- [Gap trong monitoring]
- [Gap trong runbook]

## Action Items
| Action | Owner | Due Date |
|--------|-------|----------|
| Add alert for X | | |
| Update runbook | | |
```

### 3.2 — Backwards Compatibility

Khi có user thật, mọi thay đổi đều có risk. Học cách thay đổi mà không break existing users.

**Database migrations:**
```
Không bao giờ:
  - Rename column trực tiếp → break queries đang chạy
  - Drop column có data → data loss
  - Add NOT NULL column không có default → break existing rows

Đúng cách (Expand/Contract):
  1. Add column mới (nullable hoặc có default)
  2. Deploy code đọc/ghi cả hai columns
  3. Migrate data từ old sang new column
  4. Deploy code chỉ dùng new column
  5. Drop old column (safe now)
```

**API changes:**
```
Breaking changes (cần versioning):
  - Remove field từ response
  - Rename field
  - Change field type
  - Remove endpoint

Non-breaking (safe to deploy):
  - Add new optional field
  - Add new endpoint
  - Add new optional parameter
```

**Feature flags cho risky changes:**
```javascript
// Thay vì deploy và pray:
if (featureFlag.isEnabled('new-checkout-flow', userId)) {
  return newCheckoutFlow();
} else {
  return oldCheckoutFlow();
}

// Rollout từ từ:
// 1% users → watch metrics → 10% → 50% → 100%
// Rollback = tắt flag, không cần deploy
```

### 3.3 — Performance Issues Thật

Tutorial performance là benchmark giả. Production performance là user complain "sao chậm vậy?".

**Framework debug performance issue:**

```
Bước 1: Measure, không đoán
  → Sentry Performance traces
  → Database slow query log
  → Server response time per endpoint

Bước 2: Tìm đúng bottleneck
  → 80% trường hợp: database query
  → 15%: missing cache
  → 5%: application code

Bước 3: Fix bottleneck đó
  → Add index → verify với EXPLAIN ANALYZE
  → Add cache → verify cache hit rate
  → Optimize query → không rewrite toàn bộ

Bước 4: Measure lại
  → Verify improvement thật sự
  → Không optimize premature
```

**Slow query checklist:**
```sql
-- Tìm slow queries
SELECT query, mean_exec_time, calls
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 10;

-- Check nếu có index
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 123;

-- Nếu thấy Seq Scan trên table lớn → add index
CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders(user_id);
-- CONCURRENTLY = không lock table khi tạo index
```

### 3.4 — Technical Debt Thật

Technical debt không phải bad code. Là quyết định conscious: ship nhanh hôm nay, trả giá sau.

**Cách track debt:**

```markdown
# Tech Debt Register

## Critical (fix trong sprint này)
- [ ] Auth token không expire → security risk
- [ ] No database backups → data loss risk

## Significant (schedule trong 2 tuần)
- [ ] N+1 query trong /api/orders → performance issue
- [ ] Error handling không consistent → hard to debug

## Minor (backlog)
- [ ] Hardcoded strings cần move vào constants
- [ ] Missing JSDoc cho public functions
- [ ] Test coverage thấp ở payment module
```

**Quy tắc không để debt tích lũy:**
```
Boy Scout Rule: Leave the code better than you found it.

Mỗi khi touch một file:
  - Fix 1 small thing bạn thấy (không phải refactor toàn bộ)
  - Add 1 test nếu chưa có
  - Remove 1 dead code

Sau 3 tháng, codebase tốt hơn đáng kể mà không có "big refactor" nào.
```

### 3.5 — User Feedback Loop

User không nói thứ bạn muốn nghe. Họ nói thứ họ thật sự gặp.

**Cách collect feedback:**

```
1. Session recording (Hotjar free tier)
   → Xem users thật sự làm gì, không phải nói họ làm gì
   → Tìm rage clicks, confusion points

2. In-app feedback (simple form)
   → "Có gì không hoạt động đúng không?" ← open-ended
   → Không survey dài, không rating stars

3. Error tracking (Sentry)
   → Thấy errors users gặp nhưng không report
   → Prioritize những lỗi xảy ra nhiều nhất

4. Direct conversation
   → Nói chuyện với 5 users mỗi tháng
   → Không defend product, chỉ nghe
```

**Prioritize feedback:**
```
Impact × Frequency = Priority

High impact + High frequency → Fix ngay
High impact + Low frequency → Investigate
Low impact + High frequency → Quick win
Low impact + Low frequency → Backlog hoặc ignore
```

## PHẦN 4 — Grow Từ Side Project Lên Production

### 4.1 — Khi nào add gì

Không add infrastructure premature. Add khi có signal thật:

```
Milestone: 10 users
  → Error tracking (Sentry)
  → Uptime monitoring
  → Basic logging
  → Automated backups
  ← đây là V1 minimum

Milestone: 100 users
  → Performance monitoring (response times)
  → User analytics (PostHog)
  → Email notifications khi có errors
  → Staging environment proper

Milestone: 1,000 users
  → Caching strategy (Redis)
  → Database read replica
  → CDN cho static assets
  → Status page (Statuspage.io)
  → On-call setup (nếu có team)

Milestone: 10,000 users
  → Load testing trước mọi major feature
  → Database connection pooling proper
  → Rate limiting per-user
  → Horizontal scaling strategy
  → SLO định nghĩa

Milestone: 100,000 users
  → Dedicated DevOps/SRE attention
  → Multi-region consideration
  → Database sharding consideration
  → Full observability stack
```

---

### 4.2 — Khi nào refactor architecture

Refactor sớm = waste time. Refactor muộn = technical debt crushing.

**Signals cần refactor:**

```
Signal 1: Tính năng mới mất nhiều hơn gấp đôi thời gian bình thường
  → Codebase đang trở thành obstacle, không phải enabler

Signal 2: Bug fix ở một chỗ, break chỗ khác thường xuyên
  → Coupling quá cao, cần tách modules

Signal 3: Onboarding developer mới mất > 1 tuần để hiểu codebase
  → Complexity quá cao so với size

Signal 4: Deployment sợ hãi, không ai muốn deploy ngày thứ Sáu
  → Thiếu tests, thiếu CI/CD confidence

Signal 5: Database queries > 1 giây thường xuyên
  → Cần index review, query optimization, hoặc caching

Không phải signal:
  ✗ "Code nhìn xấu" — subjective, không đủ lý do
  ✗ "Tôi vừa học pattern mới" — not invented here syndrome
  ✗ "Framework mới ra rồi" — rewrite cost cao
```

---

### 4.3 — Khi nào thuê/thêm người

Side project một mình học được nhiều nhất về full stack. Nhưng có giới hạn.

```
Vẫn một mình khi:
  → < 1,000 users
  → Ship velocity vẫn OK
  → Không có revenue để justify hiring

Cân nhắc thêm người khi:
  → On-call quá nặng cho 1 người
  → Một domain (frontend/backend/infra) bị neglect
  → Revenue có thể cover cost

Thứ tự thêm người (nếu product growing):
  1. Contractor/part-time cho weak spots của bạn
  2. Full-time khi có stable revenue
  3. Second engineer sau khi process đã rõ
```

## PHẦN 5 — Checklist Tự Đánh Giá

Đây là dấu hiệu bạn đã thật sự "ship" chứ không phải chỉ "deploy".

### Level 1 — Deployed (chưa phải Ship)
- [ ] App chạy trên production URL
- [ ] Mình có thể dùng được
- [ ] Không crash ngay lập tức

### Level 2 — Launched (bắt đầu Ship)
- [ ] Có ít nhất 5 users không quen biết đang dùng
- [ ] Có error tracking — biết khi có lỗi
- [ ] Có backups — không sợ mất data
- [ ] Auth hoạt động đúng và secure
- [ ] HTTPS enabled

### Level 3 — Production (thật sự Ship)
- [ ] > 50 users active trong tháng
- [ ] Đã xử lý ít nhất 1 production incident
- [ ] Đã làm ít nhất 1 database migration trên production data thật
- [ ] Có monitoring — biết app đang hoạt động thế nào
- [ ] Có feedback từ users — biết họ muốn gì tiếp theo
- [ ] CI/CD pipeline — không deploy bằng tay

### Level 4 — Sustainable (Ship đúng nghĩa)
- [ ] > 200 users hoặc revenue cover costs
- [ ] Đã viết postmortem cho ít nhất 1 incident
- [ ] Codebase đủ clean để quay lại sau 3 tháng không bị mất phương hướng
- [ ] Tech debt được track và prioritize
- [ ] Performance được monitor, không chỉ "hình như chạy được"
- [ ] Security được review ít nhất 1 lần bởi người khác (hoặc security checklist)

### Level 5 — Scaling (Giai đoạn 4 hoàn thành)
- [ ] Đã xử lý traffic spike không expect
- [ ] Đã phải make architecture decision dưới áp lực thật
- [ ] Đã break production và fix được trong SLA
- [ ] Có người dùng phụ thuộc vào app — không thể down tùy ý
- [ ] Đã phải explain technical trade-off cho non-technical stakeholder

## PHẦN 6 — Những Bài Học Không Có Trong Tutorial

Đây là thứ chỉ biết được sau khi ship. Đọc trước để chuẩn bị tâm lý.

---

**"Shipped is better than perfect"**
Version 1 sẽ xấu. Codebase sẽ có những chỗ bạn muốn rewrite ngay. Ship nó đi. Feedback từ real users quan trọng hơn code perfect không ai dùng.

---

**"Users don't do what you expect"**
Bạn design một flow rõ ràng. Users sẽ tìm cách dùng khác. Session recording sẽ làm bạn ngạc nhiên. Đây không phải bug — đây là insight.

---

**"The bug you can't reproduce is the worst bug"**
User report bug, bạn không reproduce được. Đây là lúc structured logging và error tracking prove worth. Nếu không có context trong logs, bạn đang debug mù.

---

**"Premature optimization is the root of all evil"**
Không optimize trước khi có data chứng minh cần optimize. Hầu hết performance issue bạn lo ngại sẽ không xảy ra. Những gì thật sự slow sẽ là thứ bạn không expect.

---

**"Technical debt compound như lãi suất"**
Debt nhỏ hôm nay, được, có lý do. Nhưng nếu không pay off, nó compound. 6 tháng sau, thêm feature nhỏ mà mất 3 ngày vì phải navigate debt cũ. Đó là khi bạn hiểu tại sao track và address debt định kỳ không phải optional.

---

**"Rollback is not failure"**
Rollback là strategy đúng khi deploy có vấn đề. Engineers giỏi rollback nhanh, investigate kỹ, re-deploy đúng. Engineers không có kinh nghiệm cố fix trực tiếp trên production.

---

**"On-call teaches humility"**
Khi bạn là người nhận alert lúc 3 giờ sáng, bạn sẽ nghĩ rất khác về monitoring, runbooks, và code clarity. Mọi decision về observability đột nhiên trở nên rất personal.

---

**"Documentation is a gift to your future self"**
3 tháng sau khi viết một đoạn code phức tạp, bạn sẽ không nhớ tại sao viết vậy. ADR, comments giải thích "tại sao" (không phải "cái gì"), runbooks — tất cả là đầu tư vào tương lai.

---

**"Users forgive bugs. Users don't forgive data loss."**
App down vài phút — users hiểu. Mất data của users — không recover được trust. Backups và data integrity là non-negotiable từ ngày 1.

## Kết — Sau Giai Đoạn 4

Sau khi ship một product thật qua Level 3-4 trong checklist, bạn có thứ không thể học từ sách: **judgement**.

Judgement là biết khi nào cần optimize và khi nào "đủ tốt rồi". Biết khi nào add complexity và khi nào remove nó. Biết khi nào follow best practice và khi nào pragmatically ignore nó vì context.

Đây là thứ phân biệt Senior với Staff/Principal — không phải biết nhiều hơn, mà là judge tốt hơn.

Lúc này bạn có thể quay lại Giai đoạn 3 (System Design) với một lăng kính khác. Những concepts về distributed systems, caching, scalability giờ có meaning thật vì bạn đã gặp version nhỏ của những vấn đề đó trong production thật.
