Giai đoạn 1 và 2 có câu trả lời đúng/sai rõ ràng. Giai đoạn 3 thì không.

Khi được hỏi "nên dùng microservices hay monolith?", câu trả lời Senior biết là: **phụ thuộc**. Phụ thuộc vào team size, traffic, deployment frequency, domain complexity, operational maturity. Giai đoạn 3 là học cách phân tích context đó để đưa ra quyết định có lý do rõ ràng — không phải học thuộc pattern rồi áp dụng mù quáng.

1. Pattern này giải quyết vấn đề gì?
2. Trade-off là gì — đổi lấy thứ gì để được thứ gì?
3. Khi nào KHÔNG nên dùng?
4. Dấu hiệu nhận ra khi nào cần nó?

## PHASE 1 — Frontend Architecture

### 1.1 — Design System

- 🔴 Design tokens — spacing, color, typography, shadow dưới dạng variables, không hardcode
- 🔴 Token tiers — global tokens → semantic tokens → component tokens
- 🔴 Component API design — props contract, controlled vs uncontrolled, composition over configuration
- 🔴 Variant system — `cva` (class-variance-authority) hoặc tương tự, type-safe variants
- 🔴 Accessibility built-in — keyboard navigation, ARIA, focus management từ component base
- 🔴 Dark mode strategy — CSS variables, không dùng class flip trên mọi element
- 🟡 Component documentation — Storybook, stories cho mọi state và variant
- 🟡 Visual regression testing — Chromatic, Percy — catch unintended UI changes
- 🟡 Design token sync — Figma → code pipeline
- 🟡 Theming system — multi-tenant, white-label products
- 🟡 Versioning và breaking changes — semantic versioning cho component library
- 🟡 Bundle size per component — tree-shakeable exports
- 🟢 Storybook Interaction Testing — test UI interactions trong Storybook
- 🟢 Design token tooling — Style Dictionary, Token Transformer

**Storybook Setup quan trọng:**
```
Cấu trúc tốt:
  components/
    Button/
      Button.tsx
      Button.stories.tsx      ← mọi variants, states
      Button.test.tsx         ← unit tests
      Button.module.css       ← hoặc tailwind

Stories cần có:
  - Default state
  - Mọi variant (primary, secondary, destructive)
  - Loading, disabled states
  - Error states
  - Responsive behavior
  - Dark mode
```

### 1.2 — Monorepo Architecture

- 🔴 Khi nào cần monorepo — multiple apps share code, multiple teams, shared design system
- 🔴 Workspace packages — `@repo/ui`, `@repo/types`, `@repo/config`, `@repo/utils`
- 🔴 Internal package types — publishable vs private packages
- 🔴 Turborepo task pipeline — `build` phụ thuộc `^build`, caching, parallel execution
- 🔴 Shared TypeScript config — `@repo/typescript-config`, extend trong từng package
- 🔴 Shared ESLint config — `@repo/eslint-config`, consistent rules
- 🟡 Remote caching — không build lại những gì CI đã build
- 🟡 Affected builds — chỉ build packages bị ảnh hưởng bởi changes
- 🟡 Changesets — version management, CHANGELOG generation
- 🟡 Publishing workflow — beta, canary releases
- 🟡 Circular dependency detection — `madge`, `skott`
- 🟢 Module federation — share code giữa separate deployments
- 🟢 Custom Turborepo generators — scaffold mới packages

**Khi nào KHÔNG nên dùng monorepo:**
```
- Team nhỏ (< 5 devs), 1 app duy nhất → monorepo overhead không đáng
- Các repo hoàn toàn độc lập, không share code
- Team chưa có CI/CD tốt — monorepo nhân complexity lên
```

### 1.3 — Micro-frontends

- 🟡 Khi nào cần — multiple teams, independent deploy, different tech stacks
- 🟡 Module Federation (Webpack 5) — share code giữa separate MFE apps
- 🟡 Vite Federation — Module Federation cho Vite
- 🟡 Integration approaches — iframes, Web Components, runtime integration
- 🟡 Shared dependencies — singleton instances (React, store)
- 🟡 Routing trong MFE — shell app routing vs MFE routing
- 🟡 Authentication — shared auth state giữa MFEs
- 🟡 Design system trong MFE — version conflicts, CSS isolation
- 🟢 Single-SPA — framework-agnostic MFE orchestration
- 🟢 Qiankun — MFE framework phổ biến ở ecosystem React/Vue

**Khi nào KHÔNG nên dùng micro-frontends:**
```
- Team nhỏ → coordination overhead quá lớn
- Tight coupling giữa các phần → MFE không giải quyết được
- Chưa có shared design system → UI inconsistency
- Performance-critical app → bundle duplication, load overhead
```

### 1.4 — Performance Architecture

- 🔴 Performance budget — định nghĩa: JS bundle size, LCP, INP, CLS, TTI
- 🔴 Enforce trong CI — fail build nếu vượt budget, không chỉ warn
- 🔴 Core Web Vitals monitoring — RUM data, không chỉ synthetic
- 🔴 Bundle analysis workflow — `@next/bundle-analyzer`, track regression
- 🔴 Code splitting strategy — route-level, component-level, third-party
- 🔴 Image strategy — format (AVIF > WebP > JPEG), sizing, lazy loading, priority
- 🟡 Critical CSS — inline above-the-fold styles, defer rest
- 🟡 Font strategy — `font-display: swap`, preload, subsetting, variable fonts
- 🟡 Third-party script strategy — defer, async, facade pattern
- 🟡 Edge rendering — CDN-level personalization, edge functions
- 🟡 Prefetching strategy — prefetch on hover, on viewport, on idle
- 🟢 Resource hints orchestration — dynamic preload based on user behavior
- 🟢 Speculation Rules API — browser-native prefetch/prerender

### 1.5 — State Architecture

- 🔴 State colocation — state nên sống gần nhất với nơi dùng nó
- 🔴 Server state vs Client state — phân loại đúng, tool đúng
- 🔴 Avoid prop drilling — Context, Zustand, composition
- 🔴 URL as state — filters, pagination, search — persisted, shareable, bookmarkable
- 🟡 Finite State Machines — XState cho complex UI state (wizard, stepper, player)
- 🟡 Optimistic UI architecture — pattern, rollback strategy, conflict resolution
- 🟡 Real-time state sync — WebSocket, SSE, polling — khi nào dùng cái nào
- 🟡 Offline-first state — service worker, background sync, conflict resolution
- 🟢 Event sourcing cho client — immutable state history, time-travel debugging
- 🟢 CRDTs — conflict-free replicated data types cho collaborative features

## PHASE 2 — Backend Architecture Patterns

### 2.1 — Layered Architecture

- 🔴 Controller → Service → Repository pattern — tại sao tách, không phải chỉ là convention
- 🔴 Domain logic trong Service — không trong Controller, không trong Repository
- 🔴 Repository pattern — abstract database access, swappable implementation, testable
- 🔴 Dependency injection — loose coupling, testability, không phải magic
- 🔴 Error handling per layer — domain errors vs infrastructure errors vs HTTP errors
- 🔴 Input validation ở Controller layer — không để invalid data vào Service
- 🟡 Domain-Driven Design (DDD) concepts — Entities, Value Objects, Aggregates, Domain Events
- 🟡 Application Services vs Domain Services — phân biệt
- 🟡 Port and Adapter (Hexagonal Architecture) — core logic không phụ thuộc framework
- 🟢 Clean Architecture — dependency rule, tại sao inner layers không biết outer layers
- 🟢 CQRS — Command Query Responsibility Segregation, khi nào thật sự cần

```
Ví dụ Layered Architecture:

HTTP Request
    ↓
Controller (validate input, call service, format response)
    ↓
Service (business logic, orchestrate, không biết HTTP hay DB)
    ↓
Repository (data access, không biết business logic)
    ↓
Database

Rule: Mỗi layer chỉ biết layer ngay dưới nó.
Service không import từ Controller.
Repository không import từ Service.
```

### 2.2 — Event-Driven Architecture

- 🔴 Events vs Commands vs Queries — phân biệt và khi nào dùng
- 🔴 Message queues — BullMQ, async processing, decouple components
- 🔴 Job types — immediate, delayed, scheduled (cron), recurring
- 🔴 Retry strategy — exponential backoff, max retries, jitter
- 🔴 Dead letter queue — failed jobs sau max retries, không bỏ sót
- 🔴 Idempotency trong jobs — job chạy nhiều lần phải an toàn
- 🟡 Event bus pattern — in-process events, decouple modules
- 🟡 Pub/Sub — Redis Pub/Sub, Kafka, fan-out pattern
- 🟡 Outbox pattern — đảm bảo event được publish sau transaction
- 🟡 Saga pattern — distributed transaction qua multiple services
- 🟡 Event sourcing — store events, reconstruct state from events
- 🟢 Kafka — high-throughput event streaming, consumer groups, partitions
- 🟢 Event choreography vs orchestration — trade-offs

**Outbox Pattern (quan trọng):**
```
Vấn đề: Bạn muốn:
  1. Lưu Order vào DB
  2. Publish OrderCreated event

Nếu làm tuần tự:
  - Lưu DB thành công, publish event thất bại → inconsistent
  - Publish event trước, DB thất bại → inconsistent

Outbox Pattern:
  1. Trong cùng transaction: lưu Order + lưu event vào outbox table
  2. Worker đọc outbox table, publish events
  3. Đánh dấu event đã publish

→ Atomicity được đảm bảo bởi DB transaction
```

### 2.3 — Microservices vs Monolith

- 🔴 Modular Monolith — modules độc lập trong cùng process, bước trước microservices
- 🔴 Strangler Fig Pattern — migrate dần từ monolith sang microservices
- 🔴 Khi nào microservices phù hợp — independent scaling, multiple teams, different tech
- 🔴 Khi nào microservices là sai lầm — small team, tight coupling, premature optimization
- 🟡 Service boundaries — Domain-Driven Design, bounded context
- 🟡 Inter-service communication — REST, gRPC, message queue
- 🟡 Service discovery — làm sao services tìm nhau
- 🟡 API Gateway — single entry point, routing, auth, rate limiting
- 🟡 Distributed tracing — trace một request qua multiple services
- 🟢 Service mesh — Istio, Linkerd — networking cho microservices
- 🟢 gRPC — Protocol Buffers, bi-directional streaming, khi nào tốt hơn REST

**Quy tắc thực tế:**
```
Start with Modular Monolith.
Extract service khi có lý do cụ thể:
  - Team size > 8 người cần deploy independently
  - Scaling requirements khác nhau rõ ràng
  - Technical requirements khác nhau (Python cho ML, Go cho performance)
  
KHÔNG extract vì:
  - "Best practice"
  - Nghe có vẻ xịn hơn
  - Anticipating future needs chưa có
```

### 2.4 — Caching Architecture

- 🔴 Cache levels — in-memory (in-process), distributed (Redis), CDN, browser
- 🔴 Cache-aside (Lazy loading) — read miss → fetch → store → return
- 🔴 Write-through — write DB và cache đồng thời, luôn consistent
- 🔴 Write-behind (Write-back) — write cache trước, async write DB sau
- 🔴 Cache invalidation strategies — TTL, event-based, versioned keys
- 🔴 Cache key design — hierarchical, predictable, include version
- 🔴 Cache stampede (Thundering herd) — nhiều requests miss cache cùng lúc
- 🟡 Cache-aside với locking — mutex/semaphore để tránh stampede
- 🟡 Probabilistic early expiration — refresh cache trước khi expire
- 🟡 Read-through cache — cache layer tự fetch khi miss
- 🟡 Cache warming — pre-populate cache trước khi traffic vào
- 🟡 Multi-level cache — L1 in-process + L2 Redis
- 🟢 Cache eviction policies — LRU, LFU, FIFO — khi nào dùng cái nào
- 🟢 Consistent hashing — distribute cache keys qua multiple nodes

### 2.5 — Rate Limiting & Throttling

- 🔴 Fixed window — đơn giản nhất, có edge case ở window boundary
- 🔴 Sliding window — chính xác hơn, Redis Sorted Set implementation
- 🔴 Token bucket — allow bursts, smooth rate over time
- 🔴 Leaky bucket — fixed output rate, queue requests
- 🔴 Per-user vs per-IP vs per-endpoint rate limits
- 🟡 Distributed rate limiting — rate limit qua multiple server instances
- 🟡 Graceful degradation — rate limit exceeded → queue, not reject
- 🟡 Rate limit headers — `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `Retry-After`
- 🟢 Adaptive rate limiting — adjust based on server load

## PHASE 3 — API Design Nâng cao

### 3.1 — REST API Design

- 🔴 Resource naming — nouns, plural, hierarchical: `/users/{id}/orders/{orderId}`
- 🔴 HTTP methods semantics — GET (safe, idempotent), POST, PUT (idempotent), PATCH, DELETE
- 🔴 Status codes — đủ granular: 200, 201, 202, 204, 400, 401, 403, 404, 409, 422, 429, 500, 503
- 🔴 Error response format — machine-readable, consistent: `{ error: { code, message, details } }`
- 🔴 Pagination — cursor-based cho large/real-time data, offset cho small/static
- 🔴 Filtering — `?status=active&createdAfter=2024-01-01`
- 🔴 Sorting — `?sort=createdAt:desc,name:asc`
- 🔴 Sparse fieldsets — `?fields=id,name,email` giảm payload
- 🔴 Versioning strategy — URL `/v1/` vs header `Accept: application/vnd.api+json;version=1`
- 🟡 HATEOAS — hypermedia links trong response, discoverable API
- 🟡 Content negotiation — `Accept` header, multiple formats
- 🟡 Conditional requests — `ETag`, `Last-Modified`, `If-None-Match`, `If-Modified-Since`
- 🟡 Long-running operations — `202 Accepted`, polling endpoint, callback
- 🟡 Bulk operations — create/update/delete nhiều resources trong 1 request
- 🟢 JSON:API spec — standardized REST response format
- 🟢 OpenAPI 3.1 — spec-first development, code generation

### 3.2 — GraphQL

- 🟡 Schema design — types, queries, mutations, subscriptions
- 🟡 Resolvers — N+1 problem, DataLoader để batch queries
- 🟡 Authentication và authorization trong GraphQL — field-level permissions
- 🟡 Pagination — cursor-based với Relay spec
- 🟡 Error handling — partial success, error extensions
- 🟡 Schema stitching vs Federation — khi nào dùng cái nào
- 🟡 Persisted queries — security, performance
- 🟢 Apollo Federation — distributed GraphQL schema
- 🟢 GraphQL subscriptions tại scale — WebSocket, SSE

**Khi nào dùng GraphQL:**
```
✓ Mobile clients cần flexible data fetching
✓ Multiple clients với different data needs
✓ Rapid frontend iteration mà không cần backend changes
✓ Public API với diverse consumers

✗ Simple CRUD apps — REST đơn giản hơn nhiều
✗ Team chưa quen — learning curve cao
✗ Real-time heavy — subscriptions phức tạp hơn WebSocket
✗ File upload — awkward trong GraphQL
```

### 3.3 — API Security

- 🔴 Authentication vs Authorization — xác thực ai vs kiểm tra quyền làm gì
- 🔴 Input validation — validate mọi input ở API layer, không tin client
- 🔴 SQL injection prevention — parameterized queries, ORM
- 🔴 IDOR (Insecure Direct Object Reference) — kiểm tra ownership, không chỉ authentication
- 🔴 Mass assignment — whitelist fields được phép update
- 🔴 Sensitive data — không log passwords, tokens, PII
- 🔴 CORS configuration — không dùng `*` trong production
- 🟡 API key management — rotation, scoping, revocation
- 🟡 Webhook security — signature verification, replay attack prevention
- 🟡 Request signing — HMAC signatures cho internal APIs
- 🟢 mTLS — mutual TLS cho internal service communication

### 3.4 — API Reliability

- 🔴 Timeouts — set timeouts cho mọi external calls, không để hang
- 🔴 Retries — exponential backoff, jitter, chỉ retry idempotent operations
- 🔴 Circuit breaker — fail fast, prevent cascade failures
- 🔴 Fallbacks — graceful degradation khi service unavailable
- 🔴 Health checks — `/health` endpoint, readiness vs liveness
- 🟡 Bulkhead pattern — isolate failures, prevent resource exhaustion
- 🟡 Timeout hierarchy — total timeout > per-attempt timeout
- 🟢 Chaos engineering — intentionally inject failures, test resilience

## PHASE 4 — Distributed Systems Concepts

### 4.1 — Fundamentals

- 🔴 Fallacies of Distributed Computing — 8 assumptions sai lầm thường gặp
- 🔴 Network partitions — mạng có thể fail, nodes có thể không reach nhau
- 🔴 Partial failures — một phần hệ thống fail, phần còn lại vẫn chạy
- 🔴 Latency — network latency thật, không phải zero
- 🔴 Clock synchronization — đồng hồ các machines không synchronized, không dùng timestamp để ordering
- 🔴 Idempotency — operations có thể retry an toàn
- 🟡 Consensus — làm sao các nodes đồng ý với nhau (Raft, Paxos concepts)
- 🟡 Leader election — chọn một node làm primary
- 🟢 Byzantine fault tolerance — nodes có thể gửi thông tin sai

**8 Fallacies of Distributed Computing:**
```
1. The network is reliable           ← nó không reliable
2. Latency is zero                   ← luôn có latency
3. Bandwidth is infinite             ← bandwidth có giới hạn
4. The network is secure             ← không phải mặc định
5. Topology doesn't change           ← nó thay đổi
6. There is one administrator        ← có nhiều teams
7. Transport cost is zero            ← serialization, network costs
8. The network is homogeneous        ← nhiều loại hardware, software
```

### 4.2 — CAP Theorem & Consistency Models

- 🔴 CAP Theorem — Consistency, Availability, Partition Tolerance — chỉ được 2 trong 3
- 🔴 CP systems — consistent và partition tolerant, có thể unavailable khi partition
- 🔴 AP systems — available và partition tolerant, có thể inconsistent
- 🔴 Eventual consistency — nodes sẽ đồng nhất nhau cuối cùng, không ngay lập tức
- 🔴 Strong consistency — mọi read thấy kết quả của write gần nhất
- 🟡 PACELC theorem — mở rộng CAP, xem xét cả latency
- 🟡 Consistency levels trong databases — Read Committed, Repeatable Read, Serializable
- 🟡 Linearizability — strongest consistency model
- 🟡 Causal consistency — preserve causal ordering
- 🟢 Conflict resolution — last-write-wins, vector clocks, CRDTs

### 4.3 — Scalability Patterns

- 🔴 Horizontal scaling (Scale out) — thêm nodes, stateless services
- 🔴 Vertical scaling (Scale up) — máy to hơn, giới hạn và downtime
- 🔴 Stateless services — không lưu state trong process, dễ horizontal scale
- 🔴 Session externalization — lưu session vào Redis, không in-memory
- 🔴 Load balancing algorithms — round-robin, least connections, IP hash
- 🔴 Auto-scaling — scale based on metrics, không scale manually
- 🟡 Sticky sessions — route user đến cùng 1 server, cần khi state phải in-memory
- 🟡 Consistent hashing — minimize remapping khi add/remove nodes
- 🟡 Sharding — horizontal partitioning data, shard key selection
- 🟢 CQRS + Read replicas — scale reads independently từ writes
- 🟢 Multi-region deployment — data replication, latency optimization

### 4.4 — Resiliency Patterns

- 🔴 Retry với exponential backoff — không retry ngay lập tức, chờ tăng dần
- 🔴 Jitter — thêm randomness vào retry interval, tránh thundering herd
- 🔴 Circuit breaker — 3 states: Closed, Open, Half-Open
- 🔴 Timeout — tất cả external calls cần timeout
- 🔴 Bulkhead — isolate resource pools, một phần fail không ảnh hưởng phần khác
- 🔴 Fallback — khi service fail, trả về cached data hoặc default
- 🟡 Graceful degradation — feature reduction, không system failure
- 🟡 Health check endpoints — readiness (traffic) vs liveness (restart)
- 🟡 Backpressure — downstream signals upstream khi bị overwhelmed
- 🟢 Chaos engineering — Netflix Chaos Monkey concepts, failure injection

**Circuit Breaker states:**
```
CLOSED (bình thường)
  → requests pass through
  → track failure rate
  → nếu failure rate > threshold → OPEN

OPEN (đang fail)
  → reject requests ngay lập tức (fail fast)
  → sau timeout → HALF-OPEN

HALF-OPEN (đang thử recover)
  → cho một số requests qua
  → nếu thành công → CLOSED
  → nếu fail → OPEN lại
```

### 4.5 — Data Consistency Patterns

- 🔴 Two-Phase Commit (2PC) — distributed transaction, strong consistency, blocking
- 🔴 Saga Pattern — distributed transaction với compensating transactions
- 🔴 Choreography vs Orchestration Sagas — trade-offs
- 🟡 Outbox Pattern — đảm bảo at-least-once delivery
- 🟡 Idempotency keys — safe retry cho mutations
- 🟡 Optimistic locking — version field, detect concurrent updates
- 🟡 Pessimistic locking — `SELECT FOR UPDATE`, block concurrent access
- 🟢 CRDT — Conflict-free Replicated Data Types

## PHASE 5 — Database Architecture

### 5.1 — Database Selection

- 🔴 Relational (PostgreSQL) — ACID, strong consistency, complex queries, relations
- 🔴 Document (MongoDB) — flexible schema, nested documents, horizontal scale
- 🔴 Key-Value (Redis) — caching, sessions, real-time leaderboards
- 🔴 Time-series (TimescaleDB, InfluxDB) — metrics, IoT, append-heavy
- 🟡 Search (Elasticsearch, Typesense) — full-text search, faceted search
- 🟡 Graph (Neo4j) — connected data, relationship queries
- 🟡 Column-store (ClickHouse) — analytics, OLAP queries
- 🟡 Khi nào dùng multiple databases — polyglot persistence, trade-offs

### 5.2 — PostgreSQL Advanced

- 🔴 MVCC (Multi-Version Concurrency Control) — readers không block writers
- 🔴 Vacuum và autovacuum — dead tuples cleanup, bloat prevention
- 🔴 WAL (Write-Ahead Log) — durability, replication, point-in-time recovery
- 🔴 Index types — B-tree, Hash, GIN, GiST, BRIN — khi nào dùng cái nào
- 🔴 Index-Only Scans — covering indexes, avoid heap fetches
- 🔴 Partial indexes — index subset, nhỏ hơn, nhanh hơn
- 🔴 `EXPLAIN ANALYZE` đọc sâu — Rows Removed, Actual Loops, cost breakdown
- 🔴 Connection pooling — PgBouncer transaction mode, tại sao cần
- 🟡 Table partitioning — range, list, hash — query planning với partitions
- 🟡 Materialized views — precompute aggregations, refresh strategy
- 🟡 Row Level Security — policy-based access control tại DB level
- 🟡 Full-text search — `tsvector`, `tsquery`, GIN index
- 🟡 JSONB operations — query inside JSON, GIN index cho JSONB
- 🟡 pg_stat_activity — monitor active connections, slow queries
- 🟡 pg_stat_statements — track query performance over time
- 🟢 Logical replication — selective replication, CDC (Change Data Capture)
- 🟢 TimescaleDB extension — time-series data trong Postgres

### 5.3 — Database Scaling

- 🔴 Read replicas — scale reads, không writes. Replication lag awareness
- 🔴 Connection pooling — tại sao direct connections có limits, PgBouncer
- 🔴 Query optimization — indexes, query rewriting, avoid N+1
- 🟡 Vertical scaling giới hạn — khi nào cần sharding
- 🟡 Sharding strategies — range, hash, directory
- 🟡 Sharding trade-offs — cross-shard queries, distributed transactions
- 🟡 Neon, Supabase, PlanetScale — managed DB với automatic scaling
- 🟢 Citus — distributed PostgreSQL
- 🟢 Database proxy — PgBouncer, RDS Proxy, Prisma Accelerate

### 5.4 — Migration Strategy

- 🔴 Zero-downtime migrations — expand/contract pattern
- 🔴 Expand/Contract Pattern:
  ```
  1. Expand: thêm column mới, code viết vào cả hai column
  2. Migrate: backfill data cho column mới
  3. Contract: code chỉ đọc column mới, xóa column cũ
  ```
- 🔴 Backward-compatible migrations — không breaking existing code
- 🔴 Large table migrations — `pt-online-schema-change`, không lock table
- 🟡 Migration rollback strategy — không phải mọi migration đều reversible
- 🟡 Testing migrations — run trong staging với production data size
- 🟢 Blue/green database deployments

### 5.5 — Data Modeling Patterns

- 🔴 Normalization — reduce redundancy, trade-off với query complexity
- 🔴 Denormalization — improve read performance, trade-off với write complexity
- 🔴 Soft delete — `deleted_at` nullable timestamp, implications cho indexes
- 🔴 Audit trail — `created_at`, `updated_at`, `created_by`, `updated_by`
- 🔴 Optimistic locking — `version` integer, increment on update
- 🟡 Polymorphic associations — multiple types trong 1 relation, trade-offs
- 🟡 EAV (Entity-Attribute-Value) — flexible attributes, khi nào và khi nào không
- 🟡 Temporal data — `valid_from`, `valid_to`, bi-temporal modeling
- 🟡 Hierarchical data — adjacency list, nested sets, closure table
- 🟢 Event store design — immutable events, projections

## PHASE 7 — Observability & Reliability

*Bạn không thể cải thiện thứ bạn không đo được.*

### 7.1 — The Three Pillars of Observability

- 🔴 Logs — what happened, structured JSON, searchable
- 🔴 Metrics — how much, how often, how long — time-series numbers
- 🔴 Traces — how a request flowed through the system
- 🔴 Tại sao cần cả 3 — logs giải thích chi tiết, metrics alert, traces correlate

### 7.2 — Structured Logging

- 🔴 JSON logs — machine-readable, không plain text
- 🔴 Log levels đúng — `error` (needs attention), `warn` (potential issue), `info` (business events), `debug` (developer info)
- 🔴 Pino (Node.js) — nhanh nhất, structured, low overhead
- 🔴 Request ID — generate và propagate qua toàn bộ request lifecycle
- 🔴 Correlation ID — trace request qua multiple services
- 🔴 Context logging — user ID, tenant ID, request path trong mỗi log line
- 🔴 Không log sensitive data — passwords, tokens, PII
- 🟡 Log aggregation — Loki, Elasticsearch, CloudWatch Logs
- 🟡 Log sampling — high-volume endpoints, log 1% thay vì 100%
- 🟡 Structured error logging — stack trace, error code, context
- 🟢 Log-based metrics — derive metrics từ logs (Loki LogQL)

### 7.3 — Metrics

- 🔴 Types — Counter (chỉ tăng), Gauge (up/down), Histogram (distribution), Summary
- 🔴 RED method — Rate, Errors, Duration — 3 metrics cho mọi service
- 🔴 USE method — Utilization, Saturation, Errors — cho infrastructure
- 🔴 Business metrics — không chỉ technical metrics: orders/minute, signups/hour
- 🔴 Alerting — alert on symptoms (high error rate, high latency), not causes
- 🔴 Alert fatigue — quá nhiều alerts = bị ignore, chỉ alert actionable things
- 🟡 Prometheus — metrics collection, PromQL query language
- 🟡 Grafana — visualization, dashboards
- 🟡 Percentiles — p50 (median), p95, p99 — tốt hơn average cho latency
- 🟡 SLI/SLO/SLA — Service Level Indicators, Objectives, Agreements
- 🟢 Custom application metrics — business-level instrumentation
- 🟢 Capacity planning với metrics — trend analysis, predict bottlenecks

### 7.4 — Distributed Tracing

- 🔴 Trace — toàn bộ journey của một request
- 🔴 Span — một unit of work trong trace (DB query, HTTP call, function)
- 🔴 Context propagation — truyền trace ID qua service boundaries (HTTP headers)
- 🔴 OpenTelemetry — vendor-neutral instrumentation standard
- 🟡 Jaeger hoặc Zipkin — distributed tracing backends
- 🟡 Auto-instrumentation — instrument HTTP clients, DB queries tự động
- 🟡 Sampling strategies — không trace 100%, trade-off cost vs visibility
- 🟢 Trace-based testing — verify behavior từ traces

### 7.5 — SLI/SLO/SLA

- 🔴 SLI (Service Level Indicator) — metric đo quality: error rate, latency p99
- 🔴 SLO (Service Level Objective) — target cho SLI: "99.9% requests < 200ms"
- 🔴 Error budget — 100% - SLO = bao nhiêu failure được phép
- 🔴 Burn rate — nếu dùng error budget quá nhanh, alert
- 🟡 SLA (Service Level Agreement) — contract với customers về uptime
- 🟡 Error budget policy — khi hết error budget thì làm gì
- 🟢 Multi-window alerting — burn rate qua nhiều time windows

### 7.6 — Incident Management

- 🔴 On-call rotation — ai chịu trách nhiệm khi có alert
- 🔴 Runbooks — step-by-step guide xử lý common incidents
- 🔴 Postmortem — blameless, root cause analysis, action items
- 🔴 Incident severity levels — SEV1 (critical) to SEV4 (low)
- 🟡 Incident communication — status page, stakeholder updates
- 🟡 Mean Time to Detect (MTTD) và Mean Time to Resolve (MTTR)
- 🟢 Chaos Engineering — GameDay, failure injection exercises

## PHASE 9 — Performance Engineering

### 9.1 — Performance Methodology

- 🔴 Measure first — không optimize mù, profile trước
- 🔴 Identify bottleneck — tìm đúng chỗ chậm trước khi fix
- 🔴 Fix bottleneck — optimize chỗ chậm nhất
- 🔴 Measure again — verify improvement thật sự
- 🔴 Amdahl's Law — improvement bị giới hạn bởi phần không parallelize được
- 🔴 Little's Law — L = λW (số requests in-flight = arrival rate × latency)

### 9.2 — Backend Performance

- 🔴 Database query optimization — index, query rewriting, N+1
- 🔴 Connection pool tuning — pool size, timeout, queue
- 🔴 Caching strategy — identify hot data, cache at right level
- 🔴 Async processing — move slow work ra background queue
- 🔴 Pagination — không load tất cả, load theo page/cursor
- 🟡 Database query profiling — `EXPLAIN ANALYZE`, slow query log
- 🟡 Memory profiling — heap snapshots, allocation tracking
- 🟡 CPU profiling — flame graphs, hot functions
- 🟡 Load testing — k6, Artillery — validate performance assumptions
- 🟡 Stress testing — find breaking point
- 🟢 Profiling in production — continuous profiling, minimal overhead

### 9.3 — Frontend Performance

- 🔴 Core Web Vitals — LCP, INP, CLS — Google ranking factors
- 🔴 Bundle size — tree shaking, code splitting, lazy loading
- 🔴 Image optimization — format, size, lazy loading, priority
- 🔴 Critical rendering path — inline critical CSS, defer non-critical
- 🔴 JavaScript execution cost — parse time, execution time
- 🟡 Memory leaks — detached DOM nodes, event listeners, closures
- 🟡 React performance — unnecessary re-renders, virtualization
- 🟡 Network optimization — HTTP/2, resource hints, CDN
- 🟡 Service Worker caching — offline, cache strategies
- 🟢 WebAssembly — performance-critical code

### 9.4 — Load Testing

- 🔴 Định nghĩa performance targets trước — không test mà không có baseline
- 🔴 k6 — JavaScript load testing tool, code-based scenarios
- 🔴 Test types — smoke (sanity), load (normal), stress (breaking point), soak (long duration)
- 🔴 Metrics trong load test — throughput (RPS), latency (p50/p95/p99), error rate
- 🟡 Realistic test scenarios — không chỉ hit 1 endpoint
- 🟡 Test environment — production-like data, production-like infrastructure

```markdown
# ADR-001: Chọn PostgreSQL thay vì MongoDB

## Status
Accepted

## Context
Cần database cho user profiles và orders.
Team có SQL experience, không có MongoDB experience.
Data có structure rõ ràng, relations giữa users và orders.

## Decision
Dùng PostgreSQL.

## Consequences
✓ ACID transactions cho order processing
✓ Team đã biết SQL
✓ Rich query capabilities
✗ Schema migration cần careful planning
✗ Less flexible cho unstructured data

## Alternatives Considered
- MongoDB: rejected vì team không quen, không cần flexible schema
- MySQL: rejected vì Postgres có tính năng tốt hơn (JSONB, RLS)
```

## System Design Case Studies

*Học System Design tốt nhất qua real-world examples. Mỗi case study có vấn đề, solution, và trade-offs.*

### Case 1 — URL Shortener (bit.ly)

```
Yêu cầu:
  - 100M URLs được tạo mỗi ngày
  - 10B redirects mỗi ngày (100:1 read:write)
  - URL tồn tại 5 năm
  - Redirect latency < 10ms

Key decisions:
  - ID generation: base62 encoding, distributed ID gen (Snowflake)
  - Storage: relational cho URLs, Redis cache cho hot URLs
  - Read optimization: cache top 20% URLs (80% traffic)
  - Analytics: async, không block redirect
```

### Case 2 — Real-time Chat (Slack/Discord)

```
Yêu cầu:
  - 1M concurrent users
  - Message delivery < 100ms
  - Message history, search
  - File sharing

Key decisions:
  - WebSocket cho real-time, SSE fallback
  - Message fan-out: push model (write to all subscribers) vs pull
  - Storage: Cassandra (time-series messages) + Elasticsearch (search)
  - Presence: Redis pub/sub cho online status
  - File: S3 + CDN, presigned URLs
```

### Case 3 — E-commerce Checkout

```
Yêu cầu:
  - 10K transactions/second peak
  - Inventory accuracy — không oversell
  - Payment processing
  - Order status real-time

Key decisions:
  - Inventory: optimistic locking + reservation pattern
  - Payment: idempotency keys, Saga pattern (reserve inventory → charge → confirm)
  - Database: PostgreSQL transactions cho order atomicity
  - Queue: BullMQ cho order processing pipeline
  - Real-time: SSE cho order status updates
```

### Case 4 — Feed System (Twitter/Instagram)

```
Yêu cầu:
  - 500M daily active users
  - Post và follow
  - Feed generation: see posts từ followees

Key decisions:
  Push model (fan-out on write):
    - Khi user post, write vào feeds của tất cả followers
    - Read nhanh (O(1)), write chậm (O(followers))
    - Tốt cho ít followers

  Pull model (fan-out on read):
    - Khi user đọc feed, fetch posts từ followees
    - Write nhanh, read chậm (O(followees))
    - Tốt cho nhiều followers (celebrities)

  Hybrid: push cho regular users, pull cho celebrities
```

## Dấu hiệu sẵn sàng cho Giai đoạn 4 — Ship

- Design được architecture cho một hệ thống mới và giải thích trade-offs rõ ràng
- Khi codebase chậm, biết profile đúng chỗ, không đoán
- Khi production down, biết tìm root cause qua logs, metrics, traces
- Đọc ADR của người khác và có feedback về trade-offs
- Giải thích được tại sao một quyết định architecture là đúng hoặc sai trong context cụ thể
- Estimate capacity — "với 100K users, cần bao nhiêu DB connections, bao nhiêu RAM?"
